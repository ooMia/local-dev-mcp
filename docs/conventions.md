# 개발 규약

코드·문서·설정 변경과 리뷰에 적용하는 단일 기준이다. 현재 구현을 설명하는 사실과 앞으로도 지킬 규칙을 구분한다.
사용자에게 제공하는 설정은 [설정 계약](configuration.md), Git 동작은 [Git 계약](tools/git/README.md)이 소유한다.
현재 실행 흐름은 [설계](design.md), 검사 실행 방법과 환경은 [테스트 안내](testing.md)를 참조한다.

## 문서·주석·설정의 유지 기준

유지할 내용은 다음 세 종류다.

- **규약:** 변경 시 지킬 명명·배치·경계·검증 기준. 이 문서가 소유한다.
- **사용 안내:** 지금 실행·설정·문제 해결에 필요한 절차와 제품 계약. 해당 기능의 문서가 소유한다.
- **구현 이유:** 코드만으로 알기 어려운 선택 이유·제약·주의점. 관련 코드 가까이에 짧게 둔다.

각 의미의 기준은 한곳에 두고 다른 문서는 링크한다. 코드·설정에서 바로 확인할 수 있는 파일 목록·타입 선언·
함수 설명을 문서에 그대로 복제하지 않는다. 실제 사용에 필요한 명령·입력 예시는 유지한다.
사용자가 직접 실행하는 명령과 결과 판단에 필요한 의미는 문서에 둔다. 내부 명령·fixture 이름·준비 절차의 목록은
owning code로 연결하고, 안전성·결과 의미를 설명하는 선택 이유는 해당 계약 곁에 짧게 남긴다.
과거 대화 메모·채택하지 않은 대안·미구현 계획 나열·일회성 성공 및 성능 기록·코드를 재서술하는 주석은 삭제한다.
현재 선택을 설명하는 데 필요한 근거와 검증 한계는 소유 문서에 흡수하며 별도 archive는 만들지 않는다.

설정은 현재 소비하는 코드와 사용 목적이 있을 때만 추가한다. 소비자가 없어지면 선언·예시·설명을 함께 제거한다.
기본값·생략·빈 값의 의미는 설정 계약에 명시하며, 잘못된 명시값을 자동 대체하지 않는다.
사용자 값·호환성·실제 접근 권한이 바뀌는 설정 삭제는 단순 문서 정리와 구분해 결정한다.
설정의 의미·필수 조건·기본값·우선순위·권한·적용 시점·실패 계약은 configuration.md가 소유한다.
값 획득 CLI·발급 경로·조회 결과의 선택 기준은 .env.example이 소유한다.
예시 편집에 필요한 짧은 필수 조건·생략/빈 값 안내는 변수 가까이에 반복할 수 있다.
긴 권한 모델·수명주기·우선순위 설명은 설정 계약으로 연결한다.
design.md는 여러 module의 연결 흐름·선택 이유를, configuration.md는 사용자 시작·종료·진단·정리 보장을 소유한다.
같은 동작의 원리와 운영 계약을 연결할 때는 소유 문서로 링크하며 종료 코드 표·보장 조건을 복제하지 않는다.

## 책임과 배치

시스템 바이너리 전용 구현은 공개 MCP 기능·내부 지원 모두 `tools/<바이너리명>/`에 둔다.
Python 폴더명에서만 하이픈을 밑줄로 바꾸며 실제 실행 이름·정책 이름은 유지한다.
GnuPG 보조 조회·서비스 지원은 기능 소유자인 `tools/gpg/`에 속한다. 개별 daemon마다 설정이나 폴더를 만들지 않는다.
순수 Python 기능은 업무 의미로 분류한다. 폴더는 실제 구현이 필요할 때 만든다.

도구만 공유하는 보조 함수는 `tools/`, 특정 바이너리 전용은 해당 폴더,
서버 시작과 도구가 공유하는 지원은 애플리케이션 루트에 둔다. CLI·runtime·서버는 조립을 맡는다.
시작·설정 snapshot 조립은 `app/`, MCP 서버 조립·등록·호출 interface는 `mcp/`, 기능은 `tools/`가 소유한다.
`settings`·`readiness`·오류·실행 환경처럼 조립과 기능이 공유하는 값 계약은 루트에 둔다.
`app`·`mcp`의 package init은 조립 module을 eager import하지 않는다. CLI의 환경 격리 후 서버 import 순서를 유지한다.
복수 바이너리를 조합하는 기능은 업무를 주도하는 쪽이 소유한다.
CLI 명령은 불변 정의와 수동 목록으로 선언하고, 인자 해석·handler 선택을 Policy 준비 및 실행과 구분한다.
프로세스 실행·취소는 라이브러리를 활용하며 새 범용 실행 프레임워크를 미리 만들지 않는다.

Git은 `facades → commands → 실행 지원`으로 의존한다. 하위 실행 지원은 상위 조합을 import하지 않는다.
`commands/<subcommand>.py`의 일반 함수가 현재 사용하는 고정 argv와 Git 고유 출력 해석을 소유하고,
facade가 작업 순서와 공개 결과를 조립한다. 옵션 조합마다 클래스·파일을 만들지 않는다.
경로·메시지 같은 대상 인자와 선택 옵션을 구분하고, 선택 옵션은 keyword-only로 표현한다.
고정 조합의 핵심 의미는 함수명에, 필요한 전제·제약은 docstring에 둔다. 파서·안전한 실행 계약에 묶인 옵션은 고정한다.

## 이름과 package 경계

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| MCP 도구·소유 파일 | snake_case, 같은 이름 | `get_project_head`, `get_project_head.py` |
| 실행 클래스 | PascalCase + Tool | `GetProjectHeadTool` |
| 정의 상수 | UPPER_SNAKE_CASE | `GET_PROJECT_HEAD` |
| 반환 타입 | 데이터의 의미 | `ProjectHead` |

내부 지원 파일은 공개 도구명 규칙의 대상이 아니다.
다른 package가 실제 사용하는 이름은 package 루트의 명시적 import·`__all__`로 제공한다.
경량 import가 필요한 `mcp.registry`·`tools.gpg.configuration`은 공개 module로 명시적으로 import할 수 있다.
모든 하위 폴더에서 같은 이름을 반복 재수출하거나 숨김용 forwarding 함수·호환 alias를 추가하지 않는다.

production의 package 간 소비와 공유 테스트 helper는 제공 interface를 사용한다.
동일 도구 내부의 조합과 해당 구현의 실패 주입 테스트는 내부 module을 사용할 수 있다.
`__all__`은 제공 계약이며 접근 통제·MCP 등록이 아니다. wildcard import는 사용하지 않는다.
설정 타입만 필요한 의존은 type-only import로 두고 import 시 설정 읽기·SDK 초기화가 섞이지 않도록 한다.
설치 진입점은 사용자나 외부 프로그램이 독립 실행 파일로 호출해야 할 때만 추가한다.

## 도구 정의와 호출 경계

도구 하나는 불변 정의 객체 하나에 대응한다. 정의에는 Policy·호출별 상태를 보관하지 않고 서버마다 실행 객체를 만든다.
공개 선택은 `mcp/server.py`의 수동 `TOOLS` 목록으로 관리하며 파일·export에서 자동 추론하지 않는다.
등록 이름의 중복은 객체 생성·등록 전에 거부한다. 목록을 자동 병합하거나 덮어쓰지 않는다.
바이너리 요구는 `required_commands`로 선언하고, 바이너리 유무에 따른 상속 계층은 만들지 않는다.
디렉터리명이나 annotation은 권한의 근거가 아니다. 명령 허용의 실제 범위는 설정 계약을 따른다.
선택 인자에 따라 실행 대상이 정해지는 CLI 작업은 모든 recipe의 권한을 합쳐 도구 전체를 막지 않는다.
workspace 권한·strict 입력 검증 뒤 선택한 recipe의 고정 권한과 준비 상태를 검사하고 실행 직전에 다시 확인한다.

파일 도구의 공통 접근·원문 관측·탐색 필터는 tools/workspace에서 공유하고 발생 지점마다 복사하지 않는다.
읽기 전용 기능도 실제 접근 직전 권한·대상 경로를 확인한다. 제품 상한·참조의 수명과 격리 의미는
[Workspace 계약](tools/workspace/README.md)을 따르며 Chat 대화 ID나 OS snapshot의 보장으로 확대하지 않는다.

실행 객체는 구체적인 인자·반환 타입의 async `execute` callable을 제공한다.
입력은 평평한 JSON 필드이며 공유 annotation·Pydantic 제약에서 schema와 strict 검증을 함께 생성한다.
잘못된 타입·알 수 없는 필드를 거부하고, 누락·잘못된 경로를 전체 workspace로 보정하지 않는다.
의도적으로 선언한 생략·null·기본값은 유효한 입력으로 유지한다.

공개 호출 순서는 **권한 middleware → 정적 준비 상태 → strict 입력 검증 → Depends 준비 → 본문**이다.
시작 시 고정한 설정은 실행 객체가 보유하고, 호출별 준비는 서버 설정에 결합한 Depends provider가 맡는다.
생성자는 상태를 결합하며 실제 작업은 해당 권한 검사를 거친다.
provider와 본문은 공통 안전한 오류 처리 경로를 사용하고 취소는 일반 실패로 삼키지 않는다.
provider 오류는 본문보다 먼저 발생하므로 본문 래퍼만으로 안전한 진단을 보장하지 않는다.

내부 조합은 MCP를 재호출하지 않고 Python 함수·본문에 준비값을 명시적으로 전달한다.
Depends 기본값의 자동 해석을 일반 Python 호출에서 기대하지 않는다.
공통 바이너리 실행 경로도 workspace·명령 정책을 검사한다. 실제 경로 포함·symlink·Git 상태는 작업 의미에 맞게 검증한다.
직접 명령 허용을 모든 간접 실행의 격리로 설명하지 않는다.
쓰기 실패를 무변경으로 해석하거나 자동 재시도하지 않는다. 부분 성공과 후속 관측 실패는 구분한다.

## 오류와 None

공통 오류 형식·CLI 종료 코드·범용 오류군은 루트 `errors.py`, 도구 전용 오류는 `tools/<도구>/errors.py`가 소유한다.
도구별 클래스는 공통 오류군을 상속하고, 상황별 classmethod로 안전한 원인·수정 안내를 구성한다.
연관 메서드는 모아 주석으로 구분한다. 사용자 조치가 다른 상황을 묶되 조건문마다 factory를 만들지는 않는다.
검증·파일 접근·기본값 선택은 설정 module, 진단 생성은 오류 factory가 담당한다.
factory는 설정을 다시 읽거나 검증하지 않으며 실제 identity·키·credential 값을 받지 않는다.
실행 파일 부재·명령 미허용 같은 공통 의미에는 공통 factory를 사용한다.
MCP 도구 오류와 CLI 종료 코드를 혼동하지 않으며, 외부 원문·임의 예외를 안전한 오류 문구에 복사하지 않는다.
기본 진단은 logging 경로로 전달하고 stdout의 MCP 프로토콜을 오염시키지 않는다.

설정 원본의 None은 검증 전 누락을 표현할 수 있다. 필수값 누락·무효·탐색 실패는 안전한 오류로 바꾼다.
공통 시작 요구의 오류는 시작을 막고, 기능 전용의 알려진 준비 오류는 그 기능에 한정한다.
준비 결과는 불변 준비값 또는 안전한 오류로 구분하며 원래 예외·cause를 snapshot에 보관하지 않는다.
예상하지 못한 내부 오류는 준비 부족으로 숨기지 않는다.
검증된 준비값에는 `signing=None`처럼 의미가 확정된 정상 비적용만 남긴다.
선언한 기본값·탐색 규칙은 적용하되 준비 실패를 None으로 바꾸어 기능을 끄지 않는다.
이 기준의 범위는 설정이며 Git probe·공개 결과·프로세스 상태의 nullable 의미는 각 계약을 따른다.

## 타입과 테스트

`src/`·`tests/`와 pytest 루트 진입점에 Pyright strict를 적용한다. 함수 인자·반환형과 클래스 데이터 필드는 명시하고,
self·cls와 타입이 분명한 지역 변수는 추론을 허용한다. 인자·반환형 표기는 Ruff로도 검사한다.
내부 값은 구체적 타입 또는 object와 타입 좁히기로 다룬다. 외부 동적 경계에서 불가피한 Any·cast는
최소 범위와 근거를 남기며 진단 억제에는 특정 코드와 이유를 적는다. 파일·테스트 전체 완화나 오류 baseline은 두지 않는다.

테스트의 검증 계층은 unit, integration, [ChatGPT E2E](../GLOSSARY.md#language)로 구분한다.
검증 계층과 병렬·직렬 실행 방식은 별개다. unit은 다른 테스트의 결과·실행 순서에 의존하지 않고 단독 실행할 수 있어야 한다.
unit은 실제 파일·프로세스 등 OS 자원에 의존하지 않고 제공된 데이터·객체·callable의 처리를 검증한다.
현재 unit 실행 프로필은 worker 준비 비용을 피하기 위해 `-n 0`을 사용하되, 단독·순서 변경·병렬 실행에서도 유효해야 한다.
integration 프로필은 `-n 4`를 사용하며 target 프로젝트의 E2E는 해당 runner의 설정으로 병렬성을 정한다.
integration은 실제 자원·프로토콜과의 연결, 접근 정책, 변환과 실패 계약을 검증한다.
integration·ChatGPT E2E의 필요한 선후·상태 의존은 DAG로 명시하며, 파일 수집 순서나 우연히 남은 상태에 맡기지 않는다.
integration·ChatGPT E2E는 별도 테스트 간 선행 결과에 따른 실행 제어를 지원한다. 이를 unit의 독립 실행 정책과 혼합하지 않는다.
후속 테스트를 선택하면 필요한 선행 테스트를 전이적으로 자동 포함하고 실행 계획에 표시한다.
합류 노드는 모든 선행 노드의 성공을 기다린다. 실행 조건을 충족한 독립 노드들은 자원 한도 내에서 병렬 실행한다.
정상 모드에서 한 가지의 실패가 형제 가지나 전체 실행을 중단하지 않는다.
독립 형제 가지는 변경 가능한 자원을 분리하거나 서로 변경하지 않는 상태만 공유해 실행 순서가 결과에 영향을 주지 않도록 한다.
실제 실패·직접 차단·선행 경로 미충족에 따른 미실행을 구분하고 후속 노드를 새로운 실패나 성공으로 세지 않는다.
노드별 결과·직접 차단 부모·최초 원인·실행 여부를 보존한다. pytest adapter의 집계 결과만으로 노드 보고를 대체하지 않는다.
fail-fast의 전역 중단은 의존성에 따른 가지 차단과 별도 정책으로 둔다. 개별 부모의 성공을 전체 하위 검증의 성공으로 해석하지 않는다.
독립 병렬 실행과 의존성 관리 도구가 함께 동작하지 않으면 테스트 방식별 실행 경로를 분리하고 각 경로에 필요한 설정·플러그인만 적용한다.
ChatGPT E2E는 시나리오 간 직렬로 실행하고 시나리오 내부의 독립 노드는 병렬 실행을 지원한다.
실제 Chat 호출이 없는 로컬 실행은 ChatGPT E2E의 완료 증거로 삼지 않는다. 준비·정리는 명시한 의존 관계를 포함해 수명을 소유한다.

테스트는 소스의 소유 package·주요 module과 대응시킨다. private 파일마다 테스트를 만들거나
commands/facades 구조를 기계적으로 복제하지 않는다. 위치만으로 검증 계층을 판정하지 않고 marker로 명시한다.

| 위치 | 검증 책임 |
| --- | --- |
| `tests/app/` | CLI·시작 조립·import 경계 |
| `tests/mcp/` | MCP 등록·schema·공통 호출 경계 |
| `tests/test_<module>.py` | 루트 설정·준비 상태 등의 소유 module |
| `tests/tools/<도구>/` | 해당 도구 동작·설정·실행 제약 |
| `tests/system/` | 실제 stdio·전체 사용자 흐름·설치 경계 |
| `tests/e2e/` | 실제 ChatGPT 호출이 필요한 수용 절차 |
| `tests/support/` | 공유 builder·타입·fixture·DAG 지원 |

파일명은 `test_<검증대상>.py`, 함수명은 `test_<동작>_<조건>`을 기준으로 한다.
공유 helper는 tests.support package에서 명시적으로 import하고 다른 테스트 파일에서 가져오지 않는다.
한 파일에서만 쓰는 fixture는 그 파일에, 같은 기능에서 공유하면 해당 conftest.py에 둔다.
여러 폴더가 공유하는 fixture는 루트 conftest.py가 제공하며 sys.path·pythonpath 우회를 넣지 않는다.
pytest 실행 방식에 결합한 fixture는 명시적으로 등록한 기능별 plugin이 소유할 수 있다. CLI 옵션을 등록하는 plugin은
저장소 루트에서 초기 로딩해 옵션 값이 기존 디렉터리여도 테스트 수집 전에 인식되도록 한다.
fixture 위치는 사용 범위, scope는 비용·상태 격리·정리 요구에 맞춘다. 실제 구현·fake·mock 선택과 fixture 수명은 별개다.
일반 workspace 준비는 Git 명령 권한·identity를 묵시적으로 추가하지 않는다. Git·commit이 필요한 검사는
해당 명령 허용과 identity·서명 준비를 명시해, 검증하려는 입력·실행 단계보다 앞선 준비 오류로 가려지지 않게 한다.
변경 가능한 workspace는 테스트별, 일반 GPG 자원은 worker별로 격리하고 상태 변경 사례는 자기 전용 자원을 쓴다.
fixture가 준비·정리를 소유하며 독립 테스트·시나리오 사이에 변경 가능한 상태를 재사용하지 않는다.
사용자 .env·키·공유 서비스는 테스트 자원으로 사용하거나 정리하지 않는다.

폴더 분류나 Git·GPG 사용 자체는 순차 실행의 근거가 아니다.
공유 자원 충돌은 먼저 격리하고, 불가능할 때만 대상 자원과 이유를 명시해 같은 worker 묶음 또는 별도 실행을 선택한다.
같은 worker 묶음은 전역 배타 실행이 아니다. 암묵적인 상태 의존을 실행 순번 marker로 숨기지 않는다.
개발 환경 회귀와 실제 설치 검증, 로컬 MCP와 실제 Chat 도구 호출의 증거를 구분한다.

테스트 품질은 관측 가능한 계약과 결함 검출력으로 판단한다. mutation 검증은 핵심 처리부터 적용하고
생존 변이·동등 변이·timeout·실행 오류를 구분한다. coverage는 공백을 찾는 자료이며 수치 상승을 위해 의미 없는 검사를 추가하지 않는다.
시간은 검증 범위·준비 비용·선후 의존·worker 조건과 함께 해석하며 짧아졌다는 사실만으로 개선을 주장하지 않는다.

## Git workflow와 호환성 평가

채택 이유는 [ADR 0005](adr/0005-assessed-squash-and-batched-releases.md)와 [ADR 0006](adr/0006-native-pr-workflow-mvp.md), 입력·계산·실패 계약과 명령은
[릴리스 도구](tools/release/README.md)와 [Git 통합](tools/git/README.md#평가-기록에-근거한-main-통합)이 소유한다.

- PR 출처·기본 브랜치 품질·원격 활성화는 [PR workflow 계약](tools/workflow/README.md)을 따른다.
- `main`을 기본 통합 기준으로 사용한다. 상시 `develop`이나 major/minor/patch 공유 브랜치를 만들지 않는다.
- 현재 main에서 `feat/<topic>`, `fix/<topic>`, `refactor/<topic>`, `docs/<topic>`, `test/<topic>`,
  `build/<topic>`, `ci/<topic>`, `chore/<topic>`을 만든다. 버전 준비만 `release/X.Y.Z`를 사용한다.
- 각 작업은 실제로 바뀌는 계약·소스·테스트·문서를 함께 다루며 작은 commit을 자유롭게 만들 수 있다.
  통합 직전에 현재 main을 포함하도록 정리하고, 검증된 작업 단위를 최종 메시지 하나로 squash한다.
- 이번 변경의 평가 파일을 새로 추가한다. 기존 main에 평가가 남아 있다는 사실은 이번 변경을 평가했다는 뜻이 아니다.
  `none`도 근거를 적는다. 기존 기록을 수정·삭제하지 않고 명시적 정정 관계를 새 파일로 남긴다.
- 일반 통합에서 version·완성 changelog·릴리스 영수증을 바꾸지 않는다. 릴리스 때 미소비 기록의 유효 최대 영향과
  원인을 조회하고 정확한 HEAD·계획 digest로 준비한다. 새 변경이 통합되면 이전 release 준비를 그대로 재사용하지 않는다.
- 최종 제목은 `type(scope): 변화` 형식을 사용하고 비호환 의도가 있으면 `!`로 드러낼 수 있다.
  버전 계산의 원장은 명시적 평가 기록이다. commit type이나 `!`만으로 실제 호환성을 판정하지 않는다.
  본문은 문제·이유, 달라진 동작, 보장의 경계, 검증을 설명한다. 대화 순번·실험 체크포인트로 목적을 대신하지 않는다.
- 검증한 release commit에 버전 태그를 붙이고 artifact를 게시하는 단계는 명시적으로 실행한다.
  일반 병합·release prepare를 tag·게시 성공으로 취급하지 않는다.

### 사용자 또는 에이전트가 명시적으로 판단하는 부분

SemVer의 기준은 마지막 보호 대상 릴리스의 공개 계약이다. origin/main은 이력 재구성의 부모일 수 있지만
사용자가 실제 설치한 마지막 artifact를 자동으로 대신하지 않는다.

1. **공개 범위:** MCP의 도구명·입력/결과·기본값·오류·권한·수명, CLI 실행/종료 의미와 설정 계약을 비교한다.
   Experimental Python 모델을 안정된 외부 API로 자동 승격하지 않는다. 실제로 지원·사용한 옛 경로를
   문서가 없다는 이유만으로 소급해 내부라고 선언하지 않는다.
2. **호환성:** 기존 정상 사용이 깨지면 major, 이를 유지한 기능 추가는 minor, 기존 계약 내 오류 수정은 patch로
   평가한다. 동작·배포 영향이 없으면 none이며 단순히 docs/test/refactor라는 이름 때문에 자동 none으로 분류하지 않는다.
   보안 제한 강화나 결과 enum/필드 추가도 기존 소비 방식에 따라 비호환일 수 있다. 왜 이 분류인지 기록한다.
3. **정정·revert:** 미배포 API의 재설계, 완전한 revert, 잘못된 이전 평가가 순효과를 바꾸는지 판단하고
   `supersedes`와 근거로 정정한다. 도구는 명시한 관계를 검증할 뿐 정정의 의미가 맞는지 추론하지 않는다.
4. **안정성 선언:** 현재 0.x는 초기 개발이다. breaking/minor는 다음 minor, patch는 다음 patch를 제안하되
   실제 breaking 분류는 보존한다. 첫 1.0.0은 보호할 공개 범위를 확정한 별도 결정이다.
5. **운영 범위:** 로컬 검사·CI 실행·원격 보호·tag·게시·운영 Apply를 구분한다. 원격 보호 기능을 지원하지 않는
   환경에서도 내부 도구로 같은 검사를 실행한다. 계정/요금제/보호 설정은 개발 완료 조건으로 강제하지 않는다.

### 기존 이력의 일회성 재구성

초기 main 이후의 관련 변경은 계약별 의미 단위로 다시 묶을 수 있다. 원본 refs·미커밋 파일을 복구 가능한 사본에
보존하고 각 경계의 실제 snapshot·검사를 확인한다. 최종 tree의 동일성은 별도로 검증한다. 새 workflow 구현은
기존 제품 tree 재구성과 구분한다. 미통합 WIP의 고유 SHA만 보고 이미 이식한 기능을 다시 합치지 않는다.
새 커밋은 출처와 선택 이유를 설명하며 소급해 실제 배포·검증이 있었던 것처럼 쓰지 않는다.

## 변경 완료 조건

1. 변경한 동작·입력·설정·경계·구조마다 관련 규약과 사용자 계약을 확인한다.
2. 같은 변경에서 설명·주석·예시·설정·검증을 갱신하거나 불필요해진 내용을 삭제한다. 관련 항목이 없으면 새 문서를 만들지 않는다.
3. 도구 변경은 필요한 schema·정상 동작·잘못된 인자·권한 거부·서버별 상태 격리와 안전한 오류를 검증한다.
   package·진입점 변경은 import·실제 설치 경계도 확인한다. 단순 전달 코드를 복제하는 테스트는 늘리지 않는다.
4. [검사 명령](testing.md#실행-경로)으로 타입·lint·관련 회귀를 확인하고, 변경 위험에 맞게 stdio·전체 회귀·설치 검증을 수행한다.
5. 깨진 참조·중복된 기준·소비자 없는 설정이 남지 않았는지 확인하고 검증 결과와 한계를 보고한다.

링크 검사·lint는 문서의 의미가 최신임을 증명하지 않는다. 코드와 설명을 대조하는 검토가 완료 조건이다.
