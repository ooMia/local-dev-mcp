# 최초 정리 기준선 게시

이 절차는 [ADR 0008](../../adr/0008-initial-consolidated-baseline.md)의 최초 기준선에만 적용한다.
이후 변경은 [정상 PR 통합](README.md#기능-통합)을 따른다. 이 문서는 실제 게시 완료 기록이 아니다.

## 게시 전

1. 기능별 네 커밋과 그 위의 검수 수정 커밋 하나로 후보를 고정하고, 서명·경계별 tree·전체 검사·배포물
   제외 검사를 확인한다. 최종 릴리스 계획 조회가 성공해야 한다. 버전은 이 단계에서 올리지 않는다.
2. 원본 refs와 최초 평가 bytes를 복구 bundle/사본으로 로컬에 보존한다. 원본 브랜치는 원격에 게시하지 않는다.
   출처 trailer에 적힌 원본 SHA는 새 원격 clone에서 사용할 수 없으며, 게시한 커밋의 SHA와 tree가 정본이다.
3. 별도 깨끗한 clone에 정리된 단일 브랜치만 복제하여 main으로 준비한다. 기존 저장소의 갈라진 main을
   덮어쓰거나 그 저장소의 hooks를 끄지 않는다. 이 clone에는 사용자 .env·개인 인증 파일을 복사하지 않는다.
4. 최종 보고서의 후보 SHA와 실제 HEAD, 원격 URL·기본 브랜치·현재 main SHA를 비교한다. 원격 main은
   `2ae0de2d520725b17355d0f2fca90dd64240a11d`여야 하며 후보의 조상이어야 한다. 다르면 중단하고 다시 검토한다.
5. 정확한 `HEAD:refs/heads/main` 게시와 후속 원격 설정 변경은 별도로 승인받는다. 태그·전체 refs·원본
   개발 브랜치를 함께 push하지 않으며 force 옵션을 쓰지 않는다. 이 문서나 로컬 검수 승인은 push 승인이 아니다.

새 clone은 첫 기준선 게시 전까지 일반 개발에 사용하지 않는다. 그곳에서 프로젝트 hooks를 설치하는 시점은
아래 게시 후 단계다. 이미 hooks가 설치된 곳에서 오류를 이유로 비활성화하여 게시하는 경로는 제공하지 않는다.
게시 시 기존 운영 환경이 추가 승인을 요구하거나 거부하면 이를 우회하지 않고 원인을 확인한다.

## 게시 후 확인

원격 main이 승인한 후보 SHA와 일치하는지 다시 읽는다. 응답 유실 때는 재실행 전에 원격 ref를 조회한다.
`Project checks / Project quality`의 push 실행이 성공한 뒤에만 원격 CI 성공을 기록한다. 로컬 검사가 이 실행을
대신하지 않는다. 기본 브랜치 이름은 main으로 유지하며, 기존 Draft PR이 초기 변경을 중복 게시한다면
폐기 여부를 별도로 결정한다.

게시된 main을 사용하는 clone에서 다음을 실행하고, ready=true를 확인한 뒤 후속 작업을 시작한다.

```sh
uv sync --locked
uv run --locked python -m local_dev_mcp.tools.workflow install
uv run --locked python -m local_dev_mcp.tools.workflow doctor
```

원격 병합 방법은 정상 정책에 맞춰 squash만 허용하도록 별도 승인 후 설정한다.
`configure-github`는 ruleset API를 요구한다. 비공개 저장소의 계정 조건이 지원하지 않으면 성공을 가정하거나
자동 공개 전환·요금제 변경을 하지 않는다. 이 경우 Actions·로컬 hooks·통합 CLI는 사용할 수 있지만,
원격이 검사·writer·PR 통합을 강제한다고 표현할 수 없다. 이 저장소는 비공개 유지와 이 한계를 수용했다.
추후 원격 강제가 필수로 바뀌면 지원하는 계정 조건과 실제 거부 동작을 별도로 검증한다.

현재 통합 명령의 CI 직접 확인 보완도 이번 범위에서 보류했다. 첫 게시 준비 완료는 후속 자동 PR 병합의
안전성 검증 완료를 뜻하지 않는다. 그 경계는 [정상 통합 계약](README.md#기능-통합)을 따른다.
